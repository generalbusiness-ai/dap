# Ordering: how a context gets, keeps and moves its order

Signed events and deterministic folds do not choose an order. Some mechanism
must select which concurrent submission occupies the next position and
establish when that choice is final. **The context delegates this authority
through an explicit sequencing profile pinned in its genesis.** The profile
can name a single writer or a group running an agreement protocol; either way
the applications see one logical sequencer.

This note is about that mechanism, what it asks participants to trust, and
how it changes hands. What a context *is*, and how different audiences share
its order, are the other two notes' concerns.

The first experiment is the simplest arrangement: one explicitly trusted
writer over a durable journal (§3), moved between hosts without losing
identity, positions or retry results (§6). §2 surveys the alternatives so
the choice is a choice. Three words used throughout: the **genesis** is the
signed first entry that fixes a context's identity and rules; the
**sequencing profile** is the part of the genesis that says how the next
position is chosen and who may commit it; the **assignment** is the writer
key or validator set the profile currently authorizes.

## 1. What ordering must establish

For a context with an irreversible first-effective-wins rule:

- **Agreement** — accepted committed histories are prefixes of one history;
  two readers cannot legitimately finalize different entries at one position
  within the profile's stated fault assumptions.
- **Finality** — extending the history never inserts before, or replaces, a
  committed position.
- **Attribution** — a position binds the exact submitted bytes and their
  submission proof; authorized readers can verify the original actor proof.
- **Durability and retry** — an acknowledged append survives the failures the
  profile promises to tolerate; an exact retry resolves to the same position,
  and does so even when the credential that admitted the original submission
  has since been consumed or withdrawn.
- **Progress** — the profile states whose availability and cooperation are
  needed for another append. A queued request is not a committed event.

Order chooses precedence among concurrent attempts. It does not discover
real-world arrival time, guarantee fair admission, or decide semantic
effectiveness: a withdrawal and an acceptance can both be recorded, and their
order plus the model decides the result.

The genesis (design note §2) pins the profile, the initial assignment, and
how a commitment is verified. An invitation names that genesis; accepting it
is the participant's bootstrap trust choice. A discovery URL alone
establishes nothing.

## 2. Where the sequencer can run

| Arrangement | What establishes order | What participants accept |
|---|---|---|
| One participant's device | one serialized writer and durable journal | that participant's behaviour; commits pause while it is offline |
| A selected service | the same writer contract behind an endpoint | the provider's ordering behaviour, custody, retention, availability |
| A service replicated for crash recovery | a consensus protocol commits the append state across replicas | operators follow the protocol; progress needs a functioning quorum |
| Small group countersigning | every designated signer durably agrees to the same next entry before it is final | any signer can block; at least one honest signer must refuse conflicting histories |
| A Byzantine-fault-tolerant group | a protocol commits despite a bounded number of dishonest validators | a fixed fault threshold, authenticated membership, the protocol's progress assumptions |

The first two are one protocol with different custody. Gitseq's authoritative
Git ref and Atseq's conditional PDS write are concrete single-authority
implementations; Noseq proposes the same boundary in a durable journal over
opaque submissions.[^lineage] Raft is the reference for replicated crash
recovery: a three-server configuration tolerates one unavailable server when
the remaining majority can communicate and elect a leader, and it does not
protect clients from malicious operators.[^raft] PBFT is the reference for
distrust between operators: `3f+1` replicas tolerate `f` Byzantine ones,
with progress depending on eventual communication.[^pbft] Unanimous
countersigning is the small-group tradeoff: no timeout bypasses a missing
signer, changing the signer set needs a rule agreed under the previous
configuration, and using buyers as signers would reveal their membership and
let them block each other's private work.

The participants in the application, the principals allowed to read an
event, and the nodes establishing order are three different sets. Making them
equal is a deployment choice, not a framework requirement.

### An anonymous pool

Operators can be anonymous and services interchangeable. An active assignment
still needs a verifiable signing identity — possibly a key used only for this
context and epoch. Participants need not know the operator; they must know
which proof authorizes a commitment and what behaviour they are trusting.

| Service role | How interchangeable | What establishes authority |
|---|---|---|
| Retain or relay committed entries | fetch the same bytes and proofs from any source | existing commitment evidence, not the endpoint |
| Propose the next entry | any candidate may propose; rejected ones are replaced | a designated signer set or conditional append finalizes one |
| Act as the delegated writer | select a candidate for an explicit epoch | genesis or a `dap.seq.assign` by ordering-control keys binds its key |
| Participate as a validator | candidates join through the membership protocol | the current configuration authorizes admission and defines quorum |

A proposer pool is the most interchangeable: proposals are uncommitted work
and the finalizer stays responsible for agreement. A delegated anonymous
writer receives real ordering authority and can censor or equivocate just as
a named one can; anonymity removes no trust choice. Several keys or endpoints
may belong to one operator, so sampling a pool does not establish independent
validators.[^sybil] Nostr's relay protocol, the obvious analogy, publishes and
retrieves author-signed events without establishing a shared committed
order; a pool needs the finalization rule on top.[^nip01]

**Discovery and assignment are separate.** A directory advertises endpoints,
keys, profiles, limits and retention; it cannot authorize a service by listing
it, or by reporting that another is unavailable. An assignment binds at least:
context identity and ordering epoch; exact predecessor head and the evidence
permitting continuation; writer key or validator configuration; commitment and
retention profile; authorization under genesis or the previous configuration.
For the revised movable-writer fixture `dap.fixture.single-writer/3`, the
exact predecessor is `{position, headerHash}`. The header hash binds the
entry commitment and the preceding chain; the control signature must bind
both fields. An entry commitment alone is not an exact head: an equivocating
writer could place the same committed bytes at a different position.

## 3. The minimum single-writer implementation

One authoritative journal per context with its committed head and retry index.
Many contexts may share a host; each has an independent order. The writer is
the current assignment, not a permanent part of the context's meaning.

1. The client saves the signed intent and stable action identity before
   submission. An encrypted transport also saves its exact outer envelope;
   retry never re-encrypts or manufactures a new action.
2. The writer verifies the stable facts: actor signature, destination
   genesis and envelope bounds. Nothing here depends on current membership.
3. Inside the serialized append path it checks the retry index: same identity
   and content returns the existing receipt; changed content under that
   identity is refused. This happens **before** admission, so an exact retry
   of a committed action recovers its receipt whatever has since happened to
   the credential that admitted it.
4. Only for a new action does it check **admission**: a current transport
   credential — issued by the serving party to current participants from
   folded participation — or the one-use invitation capability itself for a
   single `dap.accept_invite`. The writer never folds; the serving party
   bridges participation to admission.
5. It chooses `n+1` after committed head `H` and constructs the authenticated
   entry binding position, `H` and the submission.
6. One durable transaction — or equivalent conditional append, conditioned on
   `H` still being the head — retains the entry, advances the head, records
   the retry result, marks any invitation consumed, and records any pending
   publication. Consumption and the retry record are one write, so a crash
   between them cannot leave an invitation spent without a receipt. A lost
   race or an uncertain storage reply requires reconciliation with the
   journal before retrying.
7. Only after confirmed persistence does it return the receipt. Notifications
   and mirror publication send the saved entry and resume after a crash; they
   create no second order.

The append boundary covers asynchronous signing: two handlers must never
finalize successors of the same head. A database lock, conditional write or
consensus-backed append is the serialization primitive; a process-local queue
is insufficient if another writer can open a different copy of the journal.
Uncommitted signed candidates are never published as receipts. If the receipt
promises survival of host loss, the replication that supplies it completes
*before* the receipt; an asynchronous mirror is extra copies, not that
guarantee.

The failure cases are ordinary and central: crash before append → no receipt;
crash after append, before reply → the retry finds the entry, even for an
`accept_invite` whose invitation the append consumed; crash before
notification → the saved publication resumes. None re-runs the user's action
under a new identity. Changed content under a committed action identity is
refused, never re-sequenced.

## 4. Concurrency, dependencies and offline work

```text
Bob signs offer B ──────┐
                        ├── sequencing authority ── #41 B ── #42 C
Carol signs offer C ────┘

Alice receives B and C; Bob receives B; Carol receives C.
All three verify the same committed positions and head.
```

The authority could equally have committed C first. Both orders are valid;
once one is committed, readers cannot pick the other because they prefer its
result, and receipt order proves nothing about fairness among concurrent
requests. An auction needing a fairness rule needs that rule and its evidence
separately.

A dependent act needs its prerequisite ordered first. The simplest client rule
is to await the prerequisite's receipt. A later profile could carry signed
ordering dependencies and hold or refuse a submission until they are present;
private references inside a payload are not dependencies an opaque sequencer
can check.

An offline client can read a retained prefix and save signed proposals. Its
preview is provisional. Reconnection orders those proposals against the current
history; an intervening acceptance, revocation or attachment can make them
ineffective. A client may claim a final shared outcome offline only if it
already holds exclusive authority or commitment evidence under the profile.

## 5. One order, different audiences

The sequencer needs the bytes or commitments it orders, their submission
proofs, and the ordering configuration. It need not read the application
payload. In a replicated implementation the replicated state machine is the
*append service* — head and retry state included — and folds still run
separately over authorized views.

Every view receives the same chain of verifiable headers and only the
openings it is entitled to. Header verification must not require a hidden
recipient list or private application state. **Ordering control is its own
authority layer:** `dap.genesis` and every `dap.seq.assign` / `dap.seq.seal`
are spine system kinds with self-contained proofs, and a late joiner
receives the whole spine, so every reader verifies the ordering-control
chain without running any application fold. Application authority can only
*request* a change (`dap.seq.request`); a request never installs a writer.
The profile's keys enact it. A profile may delegate enactment to a folded
capability, at the cost that readers must then fold to verify; the default
profile does not, and the design note's invariant 19 applies to profiles
that do not.

**The header and commitment wire format is undecided** — what a header binds,
what it exposes, and how a payload commitment hides guessable content. It is
this note's decision to make before the spike, and the views note's poker row
depends on it.

There is a timing problem at the interface: **the audience derived at the
committed position may differ from what the sender predicted.** A trusted
server orders first, evaluates audience at that position, then serves. An
encrypted design must defer key release until that decision or bind release to
an agreed audience-state boundary; a key handed to a guessed recipient before
commitment cannot be recalled by later declaring the event ineffective.

## 6. Failure, forks and handover

A single writer can censor, delay, favour a submission, or sign conflicting
successors. Actor signatures stop it forging an act; its own signatures do not
stop it equivocating about order. Readers expose a fork by comparing
incompatible signed histories, including through independent witnesses;
readers kept apart may never discover it. Witnesses that merely archive
headers detect misconduct; witnesses whose approval is required before
commitment are part of the ordering protocol.

For an honest failed writer, readers continue from retained history and new
commits wait. A mirror is not automatically a successor. Resuming from an
older backup under the same key can create a second history; recovery needs
the authoritative journal and an *exclusive* right to continue it, not the
longest copy that happens to be reachable.

A **planned handover** under `dap.fixture.single-writer/3` starts from
committed position `H`. Write `h(H)` for its authenticated header preimage
hash, as defined by the fixture codec; it excludes the writer signature and
binds the entry commitment and previous header hash. In epoch `e`, the
ordering-control key signs a `dap.seq.seal` actor envelope with exactly
`{epoch: e, predecessor: {position: H, headerHash: h(H)}}`. The retiring
writer appends it at `H+1` and signs that header. The control key then signs
`dap.seq.assign` with exactly
`{epoch: e+1, predecessor: {position: H+1, headerHash: h(H+1)}, writer: successor}`.
The retiring writer appends and signs it at `H+2` through the same durable
append and retry path. The successor's first entry is at `H+3`, with
`header.prev = h(H+2)`.

Seal therefore binds the exact current head, and assign the exact seal
head. Both predecessor fields are mandatory; no extra commitment field is
needed because `headerHash` already binds it. The journal, recipient view
verifier and isolated control verifier also reject an entry commitment
appearing at more than one position, independently of the control checks.
An exact retry returns its original receipt and position; it never creates
a repeated commitment. Readers verify the transition under the previous
configuration and reject continuation under the retired one. Two client
nominations cannot both install successors in one journal: only the control
key authorizes assign, and only one assign can extend the sealed head.
Gitseq supplies sealing and continuation precedent.[^lineage]

This is the **builder design decision for Hugh** under his unattended spike
instruction, recorded at
`git:sha1:e15db5d98cd3510f3f20f06b3d0e1ec58379d2b1#git:sha1:2d7edc9c76b3d657a2a9fbb3fa6ffa819cb25492`.
The revised authenticated boundary rejects the old movable `/2` profile and
its commitment-only predecessor format. Its fixtures, pins, failures and
measurements remain evidence at their historical commits; they are not
results for `/3`. The fixed-writer O1 codec and wire bytes are unchanged.
Implementation and independent acceptance require their own recorded source
and validation boundaries.

Exact-head control signatures do not prevent an ordinary assigned writer
from signing forks, copying a database or restoring an older copy. Nor do
they prove that every required control opening was supplied. Independent
control verification assumes a complete control spine and authenticates the
provided prefix, not its freshness or status as the latest head. Comparing
retained signed histories can expose forks; readers kept apart can still
miss them. A prefix ending after seal establishes only that sealed prefix.

If the writer has disappeared without a handover, automatic replacement
requires a recovery or quorum rule *already in the profile*. "Elect whoever is
online" establishes neither that the old writer stopped nor that every
acknowledged entry was recovered. Without such a rule the honest choices are
to wait, or to start a successor context with a stated imported history and an
unresolved suffix — which is not transparent continuation.

An **ordering epoch** is a contiguous interval governed by one authorized
assignment. Epoch boundaries do not reset positions or erase retry history. An
epoch is an authorized interval, not a wall-clock lease: a larger number or an
expired timer cannot fence an old writer or recover its committed suffix. If
two clients independently nominate services X and Y to continue head `H`, both
can sign incompatible successors and neither nomination authorizes
continuation; safe replacement needs an assignment protocol that excludes
competing successors, or a common finalizer. Reconnecting a former writer
must not revive its authority.

## 7. Transitions that change scope

A context identity names its history and governance, not a server. Four
transitions have different effects on the order; the design note says what
each must preserve, and this section says how.

| Transition | Sequencing effect |
|---|---|
| **Move** the writer | same context and scope; transfer journal, commit evidence and retry state, then authorize a new epoch from an exact head |
| **Spawn** bounded work | the child is a new context with its own initial assignment; the parent continues |
| **Split** a responsibility | new contexts receive distinct responsibilities and choose their own assignments; the source keeps any remaining scope |
| **Join** responsibilities | transferred responsibilities acquire the destination's assignment; source histories remain independently verifiable |

Importing a result changes no assignment. The old configuration governs any
transfer of its authority: a service offer, directory update or newly
reachable endpoint cannot authorize its own replacement. Relocating an
unchanged signer and journal is operational and still needs exclusive access
and faithful recovery; changing the recognized signer needs verifiable
transition evidence. Neither changes application meaning because hosting
changed.

### Split protocol

1. **Describe** the transition: identity, exact source prefix, the
   responsibilities and state to transfer, retained dependencies, grants, and
   the destination's semantic and sequencing profiles. Write the complete
   destination genesis now and compute its content id; that id is the
   **destination commitment**. The genesis carries no release receipt or
   release proof. Its initial state is a pinned deterministic
   transformation of the export, or an explicitly trusted assertion.
   Preserve event identities and source references; never copy an
   exclusive right twice.
2. **Release** with `dap.scope.release` at an ordered source boundary, by an
   actor holding that capability: freeze or release the affected rights,
   commit the state export, and name the destination commitment.
   Intervening spending, reservations or grants invalidate the proposal
   unless its agreed rules reconcile them into the export. The source may
   continue unrelated work; a full split can seal it.
3. **Start** the destination: initialize its journal with exactly the
   genesis the commitment names, and adopt any origins it declares.
4. **Activate** in the activation phase that begins after genesis and any
   adopted origins. Otherwise admissible destination events may occur before
   the first effective activation, under their ordinary admission,
   authorization and effect rules. A `dap.scope.activate` attempt carries
   the release receipts and proofs. It verifies the transition, source
   identities, exact export prefixes and retained inputs pinned by the
   destination genesis, and independently verifies release authority and
   effect. Intervening events do not replace those pins. Ordinary current
   authorization and closed-context gates still apply; the mere presence of
   a non-activate event, including an ineffective event by another
   participant, cannot permanently block activation.
   An admitted unsuccessful attempt consumes a position; supplying missing
   evidence can make a later fresh attempt the first effective activation.
   Transferred rights remain dormant until that success. Neither origins nor
   intervening events may effectively exercise them; an otherwise authorized
   exercise of a transferred right is ineffective with `dormant_right`.
   After success, another activate for the same transition, with the same or
   different valid proof material, has no further effect. An exact retry of
   either a failed or a successful attempt returns that attempt's saved
   receipt without another position, even after a later activation succeeds.
   Future actions bind the destination; existing source-bound proposals are
   not retargeted.

his instruction to make normal spike decisions and complete unattended:
`git:sha1:e15db5d98cd3510f3f20f06b3d0e1ec58379d2b1#git:sha1:c2982a6e6756f4fed08e5a82acc8b05a65127745`.
It refines the earlier first-entry wording consistently with the spike
plan's ineffective-then-effective trace. It is not a design change
commissioned by the checker, nor a claim of implementation approval.
The lifecycle manifest requires a failed activation, a dormant exercise and
a successful fresh activation, and separately another participant's event
at F1 followed by successful activation, on memory and SQLite.

The **destination commitment** is the content id of the destination genesis
itself. That genesis fixes every field — foundation, runtime and sequencing
profiles, the initial assignment key, initial grants, bindings, origins,
referents — and the **transition identity**: the source genesis, the
transition manifest's content id and the transferred rights. It contains no
release receipt or release proof, so its identity does not depend on which
of several valid proofs a source produced. One release names one commitment, and a
commitment is one document, so one release admits exactly one genesis by
construction. Proof material varies and lives in the activate event, where
variation is harmless: activation is judged effective or not, and its
identity is not the context's identity. The source fold admits at most one
effective release per transition identity. This is not circular: the
genesis names the source and the transition, and the release names the
genesis; neither contains the other's receipt. A sequencing receipt proves a
release was *ordered*, not that it was *effective*: the destination verifies
the source semantics and grants that establish the release, or accepts an
attestation from a principal its own genesis names as trusted for that
purpose; otherwise an ineffective release could activate a second copy of an
exclusive right. Historical access is a separate
decision from transferring a responsibility: the recipient needs the disclosed
inputs or accepted summaries required to operate, not every source payload,
and the semantic package, role and authority bases travel with the export.

### Join protocol

Presenting two histories together is a view operation; importing a result is
a local transition; neither needs a common future sequencer. When
responsibilities must actually combine:

```text
A: ... HA ── release scope A ──╮
                               ├── activate C ── c1 ── c2 ── ...
B: ... HB ── release scope B ──╯

HA and HB keep their own orders. C records the relationship and governs
the transferred future. It invents no order between old A and B acts.
```

Each source authorizes and releases its scope for the *same* transition —
same destination, same merge rules. The destination activates only when every
required release proof is present. The join specifies how to reconcile state
namespaces, referents, duplicate imports, outstanding reservations, grants and
semantic versions: recognizing that two listings concern one guitar does not
erase two prior sales, and compatible schemas do not establish compatible
authority.

There is no free atomic transaction across independently sequenced sources.
The simple release-then-activate protocol can **block** after a source releases
and before the destination activates. A timeout cannot justify both
reactivating the source and permitting a delayed activation; recovery or abort
needs evidence and rules that exclude double authority. A non-blocking join
needs a stronger agreement protocol.

## 8. Could the framework avoid a sequencer?

For some semantics. CRDTs converge without agreeing on delivery order, at the
cost of restricting the data type and operations; they are not a general
replacement for arbitrary ordered folds.[^crdt] Accepting two competing offers
independently and picking a winner on merge turns an immediate exclusive
promise into a provisional one — a legitimate application, but a different
promise. Partitioned decision rights can avoid a broad consensus group; those
rights then determine who can finalize.

Sorting known signed events by timestamp, hash or actor is not enough: a
delayed event can sort before an already processed one, and the order is
final only with evidence that the input set is closed, an agreement protocol,
or semantics that tolerate revision. Git merging and relay delivery supply no
such evidence.

An alternative keeps most activity in causal histories and sequences only
shared decisions. It would need rules for consistent cuts, cross-stream
dependencies, and the meaning of `dap.attach` and revocation across them. One
ordered context is the simpler candidate — a deliberate coordination cost,
not a theorem that every application needs total order.

## 9. What the spike tests

**One explicitly trusted writer over a durable journal meets its declared
contract, and the context can move between writers without losing identity,
positions or retry results.**

Publish a small profile: genesis, canonical bytes, proofs, retry identity,
atomic append, and the exact durability promise. The append operation is
the one the views note's fixture already uses, run over a durable journal
instead of memory, so the order of checks cannot differ between the two
spikes; the control verifier stays separate. Keep automatic failover out;
make writer unavailability visible. Then:

- concurrent appends; exact retries after lost replies, including an
  `accept_invite` retried after its invitation was consumed and a retry from
  a principal since removed; changed content under a committed action
  identity refused; crashes around commit, consumption and publication;
  restart without rollback; hidden-payload header verification; detection of
  deliberately conflicting signed heads (detection, not Byzantine tolerance);
- an isolated control verifier given only genesis, `dap.seq.*` entries and
  headers, with packages, payloads and grant folds unavailable: it accepts a
  valid seal-then-assign handover and rejects forged, skipped, wrong-head and
  wrongly authorized transitions, repeated entry commitments, a relocated
  seal and a bare `dap.seq.request` (design note invariant 19). For movable
  `/3`, test both predecessor fields independently and reject the old `/2`
  format. This verifier assumes the complete required control spine;
- move the context between two pool candidates preserving identity, positions
  and retry results; interrupt the move between seal and assign; have two
  clients nominate two successors from one head and confirm neither alone
  authorizes continuation;
- the lifecycle: start a sale, attach the Inspection package mid-stream,
  spawn inspection work on another service, admit its result, move the
  sale's writer, and join a transferred responsibility from a second context
  under explicit reconciliation. Check that every pre-attach outcome is the
  same before and after replay, that replay preserves prior outcomes, that
  imports take effect only at their local positions,
  exclusive rights are never live at source and destination together, and two
  clients cannot install different assignments from one authority basis.
  Include stale source proposals, duplicate imports, partial releases, restart
  before activation, repeated activation after restart, a second activate
  carrying a different valid proof for the same release, a genesis that
  differs from the committed one in any field, an ineffective or
  unauthorized release, two sources exporting the same right, spending
  before activation, withheld release evidence, and recovery attempts after
  a timeout while activation may already have occurred. Check that the healthy case makes progress as well
  as that the unhealthy ones block. A deliberately blocked state is a valid
  safety result, not a claim of availability.

Report against the goal criteria of design note §0: goal 4 by running the
profile as one process on one host with no external services, creating a
context and joining it through the envelope and route; goal 1 by replay
across the lifecycle's attach.

The views note's in-memory sequencer is a fixture for a different experiment
and establishes none of this. This spike checks the attach, release and
import behaviour its lifecycle exercises; it does not establish general
view consistency or the correctness of application models. Both fixtures
use the same fixed foundation and the same bootstrap. The choices to settle before starting are the header and
commitment wire format, which decisions share a scope, the rights and their
owners in the lifecycle, and the exact durability promise of the fixture.
