# Read the open requests before each keep

Request `c44e1ad7eaf0ab60f7d1e40c90fdfb8cd33260e8` and promise `9dc1536ecef16361f8f79ae3b5d2c044a58e957c` own this head. It builds on the words of [the nothing-sent head](2026-11-01-nothing-sent.md), which named this gap as an open limit and left it open.

## What the run showed

The checker read this defect in `0232e2b0` and did not run it. I ran it on the real path before I changed any code: Chromium, a real `page.reload()`, and a local `wrangler dev` Worker of `apps/room/celld` with real scopes on loopback. `probe/before/report.json` holds the run, at `3d0f0e89`.

The person presses Comment, and the reply is lost after the scope accepts the act. The person reloads while `GET originals` fails. The page says "could not read your open requests", shows no line and no button, and leaves the form enabled. The route returns, the view stays open, and the person presses again with the same words.

- **A second entry lands.** The issue holds two comments with the same words, under two idempotency keys, signed by one key. The second request's order is `POST originals`, `POST acts`, `DELETE originals/:digest`.
- **The person learns of the first request only afterward.** The draw after the second answer shows the line "You sent a comment on issue 1 from this device. It has no answer yet."
- **The same second entry lands in two other shapes.** It lands when `GET` stays down and `POST` works. It lands when the outage outlasts the margin: six minutes after the first press, with no lock in force, a press went with no line on the screen.

So the request's premise holds. The earlier press signed its own request, so the second press is a new request by the signed-requests design, and the scope judges it alone. No signature or idempotency key can stop it. The harm this head closes is the second press itself, made while the earlier send's outcome is unknown and out of the person's sight.

## What changed

- **`keepOriginal` reads the list first.** `apps/room/page/src/data.ts` reads `GET originals` just before `POST originals`. All three send paths pass through it: both of `act`'s paths and the retained editor. `issueDeviceKey` calls `act`, so it passes through too.
- **A failed read stops the press.** The press sends nothing and keeps no row. The page says why, and the next press reads again.
- **A row of this key at this scope stops the press.** `pressStop` in the new `apps/room/page/src/open-requests.ts` holds the rule. Until the margin passes, the row stops the press, because the earlier send can still arrive. Past the margin, the row stops the press once if no draw has shown it, and the draw after the stop shows it.
- **The notice tells the truth.** `ORIGINALS_UNREAD` now says "Each new request reads them first, and it goes only when that read works."
- **The editor keeps its task.** A `CopyNotKept` in `sendStep` leaves the task where it was, with its button, and removes the unsent step. The next press signs that step again. Before this head, such a stop ended the task, so "press again" would have had no button.
- **The editor's check ends its row.** `checkEditRequest` ends the row of a step that it verified. Without this, the row of a settled step would stop the task's next step.
- **The opening stop speaks of the press.** `openingScope` said "No mutation was submitted." It now says "This press sent nothing." The checker's approval `e17a677b` named this line, and this stop comes before the read, so it holds no lock.
- **The module moves.** `lastRead` and `lockedScopes` move to `open-requests.ts`, because `original-check.ts` imports `data.ts`, and `data.ts` now needs them.
- **The design note and the witness follow.** `notes/2026-10-31-signed-requests-across-devices.md`, sections 1, 5, 8 and 9, and the words and the cost label in `apps/room/page/test/two-devices.mjs`.

## Decisions

- **A read at each press, in place of an "unknown" state.** The obvious repair stores "the last read failed" and refuses in `send`. That state leaves the person stuck until a new draw, it guards only `send`, and it still trusts a lock from the last good draw. A read beside the keep needs no state, guards every send path, and recovers on the next press. It costs one `GET originals` per press. The read and the keep go to the same object, and a list holds at most 64 rows. I chose the read: by my reading of `act`, the page already makes about six requests per act, and a person meets this stop in an outage, when a wrong send costs far more than a round trip.
- **A read only after a failed draw.** This design adds no request in the ordinary case, and I rejected it. It needs the state above, and it leaves a row that another tab made after the last draw out of sight.
- **A rule in the object at `POST originals`.** This design adds no request and closes the gap between read and keep. I rejected it for this head. It changes the route for every writer, and `dap mcp` sends several requests at one scope. It also cannot tell whether a draw has shown a row, so the case past the margin needs the page anyway.
- **A row past the margin stops a press once.** The design's lock ends at the margin, because the earlier bytes cannot land after that. But the first press can already have landed, and the design's cost, "at worst Ana comments twice", assumes the line in view. The run above shows the case with no line. `lastRead` already holds what the page's next draw shows, so the rule adds no new state. A press with the line in view still goes.
- **The press signs, then reads.** The candidate in the brief refuses to sign. The read sits beside the keep so that one line guards all paths, so a stopped press discards one signature that never leaves the page. That signature grants nothing, as with every other stop at the keep.
- **The stop before the read keeps no lock and says so.** I did not move the read above `openingScope`. That stop sends nothing, and the words now claim only this press.

## The trade and the way forward

While the read fails, this page sends no act at any scope, even when no earlier send exists. The cost falls only on a failure of `GET` alone, because the keep uses the same route and a route that is down already stopped every press. A Worker with no `/originals` routes refuses both. That is the deployment window that section 9 of the design note describes, and this head changes only its words.

The person's way forward, as the run after the repair shows it:

1. A press in the outage says "This page could not read your open requests, so it cannot tell whether an earlier request here has an answer. This press sent nothing. Press again when your connection returns. The next press reads them first." The draft stays, and the form stays enabled.
2. When the route returns, the next press finds the row and stops. The draw shows the line and **Check original request**, and the draft stays.
3. The button reports "The request landed: entry 2." The form opens, and the person decides whether to send anything more. A press then goes as a new request.

Past the margin, step 2 stops once, and the next press goes with the line in view.

Views and reads that do not send keep their behaviour: `openOriginals` still reports `failed` and keeps the last rows. A page on signed reads reads no list and keeps no copy, as before.

## Open limits

Request `4b46a085` holds the first three limits as a group, under the planner's `32f19d16`. No head is promised.

- **Two tabs in one gap.** The read and the keep are two requests. A second tab of one key that presses between them does not see the first tab's row, and both requests go. No run reached this. It is by reading.
- **A reload with no session.** A page that opens on signed reads reads no list, so it does not see an earlier row. That limit stands, because it needs a failed session and no failed list. On a local `celld` Worker, an observed reload with the session route down opened "This room did not open", with no form, so no press was possible. On a Worker that answers signed reads, a press there would send with no copy, by reading. A fix would treat `unsessioned === "no-reply"` as a lost session.
- **A line that outlives its stop.** After the person presses the button, the stop's line "An earlier request from this device here has no answer yet" stays on the screen beside "The request landed", until the next press. The run after the repair shows both. The same holds for every `not-kept` line at main. The planner's `32f19d16` winds down the word work, so this head leaves it.
- **The retained editor shows the button at the next draw.** A lock stop in the editor shows its words, and the button appears when the view opens again. The editor's own button retries, and it stops again until the row ends. The case runs a stop on the first step. A stop on a later step takes the same line of code and ran in no test.
- **A lost `DELETE` can stop an editor's next step.** If a step's answer verifies and the `DELETE` fails, the row stays, and the next step at that scope stops until the margin passes or the button ends the row. By reading.
- **The reload in the scope tests is a stand-in.** They use `openRoom` in one module, with no earlier list read. Only the probes reload a browser. The opening stop ran only on scripted replies, because the demo room's opening act passes that line.
- **`dap mcp` has no such read.** A new call there signs under custody with its own rules. The request names the page.
- **Not run.** No deployed Worker, real room or hosted endpoint ran this. `tsconfig.scope.json` did not typecheck in this worktree, because the cloned `node_modules` has no `@cloudflare/workers-types`. The gate covers it.
