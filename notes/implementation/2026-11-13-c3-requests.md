## Decisions and why

The owner gathers all outcomes, including segments, before the pure
seven-rule status reduction. It reconciles custody before publishing a
replica entry. Store or replica changes during an await discard the
candidate view. Close preserves the last reconciled view. Ownership
checks at admission, signing and dispatch prevent work after close or a
replica stop.

One timer owns retries, signing death and each 30-second send deadline.
Both the timer and completion callback check that deadline. Retries copy
kept bytes without signing. Deterministic gates witness delayed callbacks,
close during awaits, death during a draft read, a new entry during
reconciliation, and a stopped replica before dispatch.

Ruling `78016c59` amends client-note section 4 rule 5: only the latest live
signing can supply a repeated submission. A, B, A creates three signings.
Ruling `55c2133c` adds protocol refusal as rule 4 without a head barrier.
The head barriers now belong to rules 3 and 5. The client attempts the
protocol answer's head read once, then stops and freezes other statuses.
The review request must name both note amendments.

Ruling `94264f21` allows existing MCP, hosted and install callers to treat
unsent beside folded as unreadable. Their answer shapes stay unchanged.
The diff changes no authentication, route, admission or network boundary.

other calls pass `resign`. Custody uses `#kept` for a new identity and
`#resigned` for an eligible existing identity. The automatic copy path

`#kept` already checks the byte forecast, admits the unresolved count
under `store.exclusive`, then calls `store.admit` before `build`.
`#resigned` now uses that exclusive section for both eligible phases and
calls the same port before building or signing. Only a refused record
needs another count slot. A dead unresolved record already occupies one.
The port receives `bytes + RECORD_OVERHEAD`, as it does in `#kept`.
This changes no budget, bound, port shape or protocol.

SQLite already supports this call for an existing identity.
`packages/mcp/src/sqlite-custody.ts:150–160` defines `arm`: its completion
need is the charged record bound less the stored record charge, with a
minimum of zero, plus one segment row and its overhead. It adds only the
part not already reserved. `admit` at lines 257–261 ignores the caller's
forecast and runs `arm` in a transaction. Budget refusal precedes any
counter change. The existing SQLite owner covers that accounting; this
repair changes no SQLite source.

When admission succeeds but a later build or signing fails, the earlier
record keeps its raw bytes and that identity keeps its reservation.
With unchanged stored rows, repeated failed attempts hold the same fixed
completion need. Once covered, `arm` adds nothing. The identity count
retains its existing limit. Result writes consume the reserved capacity;
the terminal write releases the rest when nothing remains in flight
(`sqlite-custody.ts:243–247`, through `release` at lines 133–137).

`unadmit` stays a new-identity operation. The existing-identity path calls
no `unadmit`, so it cannot release capacity an earlier signing needs.
The `admit` port comment now requires every store to make admission for
an existing identity safe to repeat. SQLite's `unadmit` at lines 263–264
does not supply a reservation-delta rollback for an existing live record.

One parameterized witness in the existing `custody-signings.test.ts`
covers refused and dead-unresolved records. It uses real custody and
signing with a memory record store and a scripted budget refusal at

delivery counters unchanged and retain the exact earlier raw record
bytes. This witnesses ordering at the store port, not SQLite accounting.
