# C3: request status, schedule and custody endings

## What changed

This is a partial C3 checkpoint, under request `91b8bbbf` and promise
`a5598874`. It does not implement `scopeClient` yet and is not ready for
review. It starts at C2 source `8dba5200` and merges C1 `6a55ec1c` locally.
Both dependencies still need to land before the final C3 gate.

`Custody.absent` now ends an unresolved record when its latest signing is
dead. It appends `unsent` with the journal head and changes the phase to
`refused`. The latest envelope stays in the record. A repeat of `send`
without `resign` or `resubmit` returns the same end and sends nothing.
A later folded entry can still make the record `accepted`. These changes
carry section 5.5 of the client note and ruling `2c2a4bc5`.

`requestStatus` computes the six ordered rules of section 6 as a pure
function. Its input includes every outcome, including the segment, and
a prediction for each signing. A replica entry wins over custody and the
clock. A refusal waits for its head before the request returns.

`RequestSchedule` gives retries, signing deaths and send deadlines one
timer. A send expires after 30 seconds. Both its timer callback and its
completion path check the deadline, so a delayed timer cannot admit a
late answer. Closing the schedule cancels pending work and its timer.
The complete client that uses this schedule remains to build.

## Decisions and why

Read-only peer review found two gaps before the focused run. The first
status draft read only inline outcomes and could lose an earlier live
copy after its outcome spilled. The pure function now requires complete
outcome evidence. The second schedule draft could accept a late answer
before a delayed timer callback. Its completion path now checks the clock.
Each regression witnesses the fault that the review found.

The custody witnesses cover 257 lost requests, capacity release after an
absent read, reload before the first send, latest-envelope retention,
no signing or sending on a repeated unsent end, and late acceptance.
A settlement `not-found` still ends no unresolved latest signing.
The status and schedule cases use deterministic clocks and scripted
answers. They prove these client decisions, not service behavior.

The client observation skill covers functions in `observe.ts`. This
checkpoint changes none of them, so it advances no model coverage hash
and claims no new formal verification result.
