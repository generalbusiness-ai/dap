The Mac host kit has five successful native witness sequences: installation and
a first room, served TLS with four custom-anchor hostname checks, preserve
shutdown and recovery, a live-producer crash and recovery, and HTTPS MCP. These
results belong to the source checkpoints below. The endpoint-certificate repair
and targeted follow-up below resolve the signing-authority finding. The single
H3 ordinary gate passes at G. The receipt audit passes; the final manifest
records retention.

## Source and implementation

The kit adds a Mac installation path under `apps/room/celld/mac`, with
certificate generation, private configuration, service installation, project
preparation, deployment, and ordered shutdown. `docs/self-host.md` describes
the first-room sequence and maintenance commands. `docs/celld.md` describes the
runtime boundary.

The installation owns a fixed prefix and three launchd services: SeaweedFS,
celld, and Caddy. The store and runtime listeners remain on loopback. Caddy
serves the configured HTTPS origin. Installation refuses an occupied prefix or
label, checks executable paths, and retains data after a partial start. Private
credentials and the session secret stay in private files. Deployment uses the
maintained Worker and bindings rather than a substitute application.

Native attempts and review led to four narrow source corrections:

- `deploy.py:133` accepts the fixed bucket's HTTP 409 only for an exact
  `BucketAlreadyOwnedByYou` error, then requires an authenticated successful
  HEAD. Other conflicts still refuse.
- `shutdown.py:145` checks one anchored `launchctl print-disabled` entry for
  the owned label. It accepts the observed `disabled` spelling and the existing
  `true` spelling. Ambiguous or unavailable output still refuses.
- `templates/celld.plist:17` uses `KeepAlive` with `SuccessfulExit:false`. A
  normal preserve exit stays stopped; an unsuccessful exit permits restart.
  `shutdown.py:164` checks the requested node identity and
  `load.draining:false`. The template retains `RunAtLoad:true`, a 60-second

- `certificate.sh` generates an endpoint certificate with critical `CA:FALSE`

  this endpoint rejects a different hostname certificate issued with the same

## Endpoint-certificate authority repair

Review found that the historical certificate used `CA:TRUE`, `keyCertSign` and
`cRLSign`. Its online private key could issue a certificate for another host
when a client trusted it as an anchor. The earlier four-name custom-anchor
success did not prove the absence of that authority. F changes the generated
certificate to critical `CA:FALSE`, with digital signatures and `serverAuth`,
and preserves the supplied SANs and maximum 825-day lifetime. The guide now
supplies `--cacert` or `NODE_EXTRA_CA_CERTS` per command. Its optional
login-keychain instructions change SSL trust only; no actual Keychain or
browser trust installation is claimed.

The focused owner reports five passes. Its added real local Node TLS case
accepts the self-signed endpoint and refuses a different hostname certificate
signed with that endpoint's key. Repeating that unchanged named case against
the frozen `CA:TRUE` scratch source fails by `AssertionError`, `strictEqual`,
with actual `true` versus expected `false`. This distinguishes signing
authority; it does not claim a deployed-host result.

The retained synthetic experiments independently compare an explicit endpoint
anchor with a separately issued leaf. Unsandboxed native Apple policy, Node TLS
and system curl accept the `CA:FALSE` endpoint and reject its issued other-host
leaf. Their `CA:TRUE` positive controls accept the issued other-host leaf.
Apple and Node also reject a mismatching hostname. These observed accepts and
refusals establish the tested client boundary, not universal trust behavior.

The first Swift compile could not write the default module cache. Early Node
attempts failed to listen with `EPERM`; early native policy returned an
OSStatus error rather than a useful positive control. The initial LibreSSL
invocation used an unsupported hostname option. Those attempts remain
inconclusive and are not counted as certificate refusals. A scratch-cache
compile and the later unsandboxed evaluations have separate retained outputs.
LibreSSL's later chain-only check rejects the direct `CA:FALSE` endpoint as
well as the issued leaf, so this note makes no LibreSSL direct-verification
compatibility claim. Curl's actual TLS check succeeds with an explicit endpoint
certificate.

Those experiments ran over four mutable repair files above E. Later F
identifies matching source bytes; it does not create an earlier immutable
experiment checkpoint. The selected public experiment records, owner test and
mutation are retained under `operator-inputs/certificate-issuer-boundary`. The
post-closure receipt
`operator-inputs/postclosure-certificate-retention-20261029-1.json` hashes to
`07bbc816e3a694f7b4bb41dc2a53e690e5ef7a4e797746cbdf3fb36df552603a`. It records
126 public files and 325,460 bytes, exact source/destination readback and no
changes to existing operator inputs or provisional markers. It establishes
neither preregistration nor a final evidence seal. Experiment elapsed and CPU
were not measured; they remain unknown.

The new Mac overlay verifies all 3,485 public source files at F without
changing private configuration or services. The candidate-generation check
reports a matching key, `CA:FALSE`, acceptance for all four SANs and a
wrong-host refusal. The 900-day refusal creates no output files. Preflight pins

After the failed activation described above, read-only served verification
