## What a person sees

Ana is away. Una, an agent, asks Ana to approve a question and stops. Vic, a teammate, asks Ana to approve another question. Ana comes back on another device and opens the room's needs-you card:

```text
Approve or request changes on question 4: "Which file format should the import keep?".

Why it is yours: @una asked you by name.

What settles it: Your approve act on the current text closes this request, with the verdict approve or request-changes.
Waiting on this: @una.
Rule: sha256:04b9f731d50cf2f838525990ab0543d8bc75dfdbf1090a8b971a74c7ca30e2a3 acts.request-approval;items.approval-request.
Reading this item leaves it open. This list grants no permission.
‹
1 / 2
›
```

Ana presses **›** and reads Vic's request. Ana opens the Updates card:

```text
What changed since your last review

Each scope below lists its newest entries since you last pressed Mark reviewed on this device.

Mark reviewed moves your place on this device and closes nothing. Another device keeps its own place, so it shows these changes again.

Issue 1: The import fails on large files. You have not marked this one on this device. Entry 4: ask by @una (agent of @ana). Entry 5: request-approval by @una (agent of @ana). Entry 6: block by @una (agent of @ana). Entry 7: ask by @vic (person). Entry 8: request-approval by @vic (person). Entry 9: comment by @vic (person). This list leaves out 4 earlier entries.
```

Ana presses **Mark reviewed**. Both requests stay on the needs-you card. Vic then adds a comment, and Ana's next visit lists only that comment:

```text
Issue 1: The import fails on large files. New since entry 9, where you last marked it. Entry 10: comment by @vic (person).
```

Ana approves. The request leaves the list, and a new row takes its place, because the question still waits for a decision. The row has category `decision-due`, `settledBy` `decide` and `waiting` `@una`, and its `needs` reads:

```text
Decide question 4: "Which file format should the import keep?".
```

Ana presses **Decide**. Una's process ends with exit 0 and prints:

```text
Question 4 is decided. Read the record and resume: dap show sc_...:12
```

A new process reads that entry and signs `release-block` with the same key. The words above come from the run in `probe-final`, on a local Worker. The `decision-due` row comes from the `needs_you` tool, because the card lists it second and the run did not page to it.

## Design: wake an agent from the room's feed

Una, an agent, asks Ana to decide a question and stops. Una's process ends, so no model runs and no tokens burn. One small process holds the room's feed for Una: `dap issue wait 3 12`. Three days later, Ana decides on another device. The feed tells that process the lane's head moved. The process reads the record, sees that question 12 is decided, prints where, and exits 0. The harness then starts Una, and Una resumes from the record with the same key.

**The feed.** The feed is the scope's existing head stream, `GET /v1/scopes/<lane>/stream`. The page and the Counter already read it. This head adds no route and no message, so the wait needs no deploy and no hosted MCP. The process uses `observeScope` from `packages/client`, which already renews sessions, reconnects with backoff, and refuses a head hash that conflicts. This head changes one thing in that path: a failed body read now counts as an outage.

**Who may read the feed.** Any member whose read session may read that lane's summary. The scope checks the session when the stream opens and again on its own clock before every send. A session lasts at most 600 seconds, and the process asks for a new one, so a revoked key stops receiving within that window. A person outside the room gets `forbidden`.

**What the feed reveals.** One line per head: `{"at":{"seq":17,"hash":"sha256:..."}}`. It names no act, no actor and no text. The summary read that follows runs under the same session, and it decides whether to wake. A head line never settles anything.

**What wakes the process.** Three facts of the question, read from the record:

- The question is `decided`.
- The question is `withdrawn`.
- Someone chose `request-changes` on its current text. The question stays `asked`, so a wait on the state alone would never wake, and Una must revise.

An unrelated comment moves the head and wakes nothing. An approval with no decision wakes nothing, because Una must not decide for Ana.

**A wake is a hint.** The process signs no act and moves no read position. If the process or the machine was down, the next start reads the record first and wakes at once. Each reconnect also reads the record, because a stream sends the current head when it opens. A missed line therefore costs at most one reconnect.

**What I rejected.**

- **MCP `wait` alone.** It polls once a second for at most 60 seconds, so the agent's turn stays open and the model pays to call it again. It stays as the wait inside a turn. It cannot wake a process that has stopped.
- **The agent's inbox.** A `decided` notice goes to the asker's inbox, so one feed could serve many questions. A notice is an advisory delivery one hop later, it says less than the lane does, and an agent's configuration can lack an inbox. The lane's head moves at the commit of `decide`.
- **A new room-wide feed.** It needs a new route, a deploy and its own authorization rule, and the existing read already answers the question.
- **`--exec`.** Starting a command brings the recovery boundary of `notes/2026-10-01-wake-and-schedule.md`, section 4. An exit code composes in a shell, and the harness owns what runs next.
- **A webhook or a schedule.** The request leaves both for later.

**What it costs.** One open stream per waiting question. The stream adds no read while nothing moves. Node's fetch ends an idle response after 300 seconds, and the Worker sends no heartbeat, so the process opens a new stream about every 5 minutes and reads the question once each time. Over 72 hours that makes about 864 stream opens, 864 summary reads and 432 session requests, by arithmetic from the observed reconnect.

## Decisions

**Marks stay on one device.** `notes/2026-10-17-journey-views-design.md` says that `DAP_HOME` storage alone does not establish cross-device behavior. The clause asks that a returning person sees every item, and `needs_you` reads rows from the record, so it holds on any device. A new device has no marks, so its Updates card shows every scope again. It shows too much and never too little, and the card says so. The planner owns any shared store of marks.

**A question on old text names a different settling act.** The `approve` act binds the current text, so a person cannot approve a request on older text. That row names `withdraw-approval-request`, and its words say the requester closes it.

**A wake reads the record.** A head line says only that the head moved. The summary read under the same session decides, and the agent resumes from the record. A question that took a final state has left the live summary, so the command also runs one bounded item query for it.

## The deployed run

The person's part runs on the existing Worker `dap-demo`. It needs no deploy, no pin, no hosted MCP and no `dap-commons` Worker. `dap-demo` offers Register 17, so a new room there has Directory 16 and Membership 8, and `apps/views` reads both. I checked this on the deployed Worker with a new scratch room, labelled "TEST J5 scratch" in its creator's home. The Brief definition activated, both roles took `issue.approve` and `issue.decide`, and `view_needs_you` answered `empty`, not `directory-unsupported`. That room holds no issue yet, so this is a check of the room and not of the scene. The local witness used `--cohort commons` only because `--host none` requires it.

The run needs `apps/views` and `dap` from this head on the first device, Chromium or a desktop AI app that renders MCP Apps, and a browser on the second device.

1. The admin invites Ana and Vic to the scratch room. Ana joins with `dap join`. The admin enrols an agent key for Una.
2. Una accepts an offer, then runs `dap act ask`, `dap act request-approval` and `dap act block`, and starts `dap issue wait <issue> <ask>`.
3. Vic asks Ana to approve a second question and adds a comment.
4. Ana starts `DAP_HOME=<first home> node --import tsx apps/views/src/node.ts --brief <file>` and opens `view_needs_you`. Ana checks both items and their three reasons, and takes a screenshot.
5. Ana opens one item. Ana checks with `dap log <lane>` that the head did not move.
6. Ana opens `view_change` and presses **Mark reviewed**. Vic comments. Ana opens `view_change` again and checks that only the comment appears.
7. On the first device, Ana makes a device-key link. On the second device, Ana redeems it on the Page and checks that the Page lists both issues and shows each question.
8. On the Page on the second device, Ana approves Una's question and checks that `dap issue wait` is still running. Ana then decides it.
9. The harness sees exit 0 and starts a fresh process, which reads the named entry and signs `release-block`.

The Page's action forms come from the definition's offered acts, so I expect it to offer **approve** and **decide**. I read that from `apps/room/page/src/actions.ts`, and no run shows it. If the Page cannot sign them, Ana signs from the first device, and the second device's clause covers reading only.

**The witness passes** when each item shows its three reasons and its rule, Ana's reads move no head, the second device lists both items on the Page, and the wait exits 0 only on the decision.

## Open limits

- **The command line cannot enrol a device.** `dap join` takes person, agent-key and checker-key links. Only the Page redeems a `device-key` link, and that key stays in the browser, where `apps/views` cannot use it. So the needs-you card itself does not run on a second device by real commands alone. The native test and the local witness compose `invite-key` and `enrol`, and they label that step. The deployed run uses the Page on the second device, by the planner's decision `32c88ad2`. Request `c74280a46e95ee7fa442e02650c9777a077028c4` owns `dap join` taking that link.
- **Marks stay on one device.** See the decision above. The planner decided in `32c88ad2` to leave this for now.
- **The list holds 50 rows per window.** `omittedRows` counts the rest, and the card says so, but no cursor reaches them. A person settles some and reads again. The builder owns a cursor, if the planner wants one.
- **`needs_you` covers questions and changes only.** A J4 issue's check jobs produce no row, by reading `apps/views/src/repo-in-ai.ts` and `apps/room/lanes/src/issue4.ts`. I left this alone, because it is outside this request. The builder owns it.
- **A question with no Brief has no card buttons.** S4's `questionActions` offers no act on a legacy question, though its row still names `approve`. The person signs with `dap act approve`. The builder owns any change.
- **The item page still shows the row as JSON.** S4's test reads that body. The builder owns the change, at the next edit of that card.
- **The Node reconnect costs reads.** No Worker change adds a heartbeat, so an idle wait reconnects about every 5 minutes. The builder owns a heartbeat, if the cost matters.
- **The wake covers one question on one issue.** Schedules and webhook conditions come later, as the request says.
