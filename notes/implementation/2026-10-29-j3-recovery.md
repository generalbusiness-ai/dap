## Recovery decisions

`ServiceOptions.recoveryGraceSeconds` defaults to 120 seconds. The default
matches the existing runner's startup grace and leaves two minutes for an
interrupted claim writer to finish. The service accepts whole seconds from
zero to 86,400 and passes its clock and the bound to each recovery lookup.
The value controls recovery, not a job's execution limit.

The runner measures a private directory's age from its creation timestamp.
It uses the modification timestamp only when the filesystem supplies no
creation timestamp. The owner must keep the host and service clocks aligned.
A recent directory with a missing or corrupt record stays pending. After
the grace, a permanent record failure ends the service's job as `run-lost`.
The fixed `record-corrupt` diagnostic names the private record path without
copying its contents. Claim read failures follow that same bound. If the
runner cannot establish an owned directory's age, it still waits. Unavailable
engine state and temporary reads of other record files also stay pending.

The runner retains every run directory. The service retains the job's run
identity and its first kept outcome. Recovery never deletes a fence, resets
a job, or calls `run` again. A retry is a new job. A late terminal report
cannot replace an outcome already kept by the service.

`run-lost` proves no physical cancellation, drained supervisor, or closed
origin. An original creator paused before publishing its claim may later
resume. A lost decision authorizes neither replacement execution nor cleanup
based on an unauthenticated record.

The claim remains bounded at 16 KiB before the runner creates a directory.

`check-error` reason before any execution record exists. The planner's ruling

## Command output and authority

The supported ctr profile launches each configured command through the
immutable Go helper's `step` command. The helper treats argv as data and
combines the program's stdout and stderr into one output descriptor.
It preserves the configured program's exit status and leaves launch
failures on its own stderr. A failing test that writes its declared
failure line to stderr can therefore produce `failed` rather than a lost
run.

The host still refuses ambiguous setup results, status 255, timeouts, and
output overflow. Profiles that leave job stderr separate keep the existing
nonzero-status refusal. The trusted Git path, its fixed environment, and the
relay's separate user identity retain their checks. The signer and host
records stay outside the job.

The Native publication witness's failing command writes its last line to
stderr. It must leave the published branch unchanged and record
`required-check-failed`. A missing executable must still supply no completed
job step. The physical witness uses a rebuilt local TEST image containing
the changed helper. It establishes no deployment or production image.
