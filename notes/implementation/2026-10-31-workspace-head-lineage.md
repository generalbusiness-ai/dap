## Decisions and boundaries

### The sender is an outcome; the claim names the opening

Register17 emits `create-directory` from the selected confirmed `create-repository` outcome. That outcome is the Directory genesis source. The create message's `fields.claim` names the earlier signed `found` act that opened the operation. The old workspace reader required the sender itself to be `found` and compared the Destination claim with that sender. Those two facts differ in a room created through the real Register.

`workspaceRepository` now checks the installed Register incarnation and exact Directory family, the outcome's owner and kind, its confirmed own-answer basis, its selected attempt effect, and the actual creation send. It reads `fields.claim` separately. The claim must name the operation's opening in the same Register incarnation and precede the outcome. The signed act must target that Register and have kind `found`. Its operation ordinal, owner, kind and attempt bound must match the outcome. The existing seed check applies to this opening, and the Destination claim must equal it. Exact lane, native birth, repository, namespace, sibling Destination and send checks remain.

The extra fact raises the immutable-read ceiling from five to six: Directory birth, lane-creation source, selected repository outcome, Register birth, original found act and Destination birth. The overall five-second deadline and one-MiB limit for each proof remain. This is a bound on awaited proof reads, not a physical cancellation guarantee. No current summary, caller-supplied repository, legacy fallback or provider query substitutes for those facts.

The bounded consumer audit found this conflation in one production parser and three scripted ancestor factories. WorkspaceHost consumes that parser for its operation and token paths. Adjacent host, archive, creation, partition and CLI claim readers already distinguish their relevant source and claim facts. The existing native archive publication witness also expects both anchors; this work does not claim a new run of it.

This host authority predicate implements the existing creation contract. [Kernel section 7](../../docs/kernel.md#7-rule-for-adding-to-the-kernel) requires review of that boundary. The repair adds no kernel export, scope kind, capability, record, definition pin or outcome meaning. A host service may authenticate existing creation facts, but it cannot invent an answer or change replay semantics.

The mismatch is consistent with both stopped S1 head operations. No retained record proves that either historical invocation reached the old predicate. The next permitted attempt must supply the diagnosis; this source finding does not establish its historical cause.
