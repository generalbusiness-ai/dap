## How an interdiff handles a rebased version 2

**The answer.** The manifest's `base` decides. When the two versions name different bases, the interdiff compares each changed path across all four commits: base 1, integration 1, base 2 and integration 2. Each path falls in one of four groups:

| Group | What the four commits show | What the reviewer reads |
|---|---|---|
| Edited by the version | The two bases agree at this path | The patch between the two versions, and the file counts as the version's edit |
| Cannot separate | The bases differ at this path, and the two versions' patches differ | Both patches, each naming its base and integration |
| The same edit on the new base | The bases differ at this path, and the patches match apart from their line numbers | The path, with no lines |
| Changed only by the new base | Each version holds its own base's file at this path | The path, with no lines |

A real rebase with no other edit says "Version 2 makes no edit of its own: every difference comes from the new base or repeats Version 1's edit."

**When the interdiff cannot separate the two.** It says so and shows both patches. It assigns no line to either side. The words are:

```text
Cannot separate. The new base and this change both touch these files, and the two versions' patches differ. A difference between the two patches can come from the new base or from Version 2. Read both patches:
```

I read the request's "the reviewer's change" as the change under review, because the reviewer writes no change in this scene. If the request means something else, this section does not answer it.

The design packet in `notes/2026-10-17-journey-views-design.md` requires a comparison with different bases to name all four patch endpoints and its method. The band and the text do both.

**What I rejected.**

- **A direct diff of the two integrations.** It reads as the version's work, and it mixes in every line the base moved. A reviewer would blame the agent for the base's lines. This is the failure the request names, and control `rebased-as-same-base-text` shows it.
- **A merge of version 1 onto the new base, compared with version 2.** This view is the most precise in the ordinary case. It needs a merge engine in TypeScript and a rule for each conflict, and a wrong merge would present a false edit as fact. Four object comparisons can only under-claim.
- **A diff of the two whole diffs.** It works without per-file groups, but it reads as patches of patches, and base-only files add noise.
- **Rebase detection by ancestry.** A rebase and a merge of the new base look alike here, and the manifest already names the base. A walk adds reads and decides nothing the groups need.

**What the groups cost.** A patch key includes context lines, so a base edit next to the change's edit reads as "cannot separate", even when the change itself did not move. That result sends the reviewer to both patches, and it never claims a false match.

## Decisions

- **A held read signs nothing.** S6 had a second click sign a second request. Each answer's commits are immutable, so a second credential buys nothing, and a person switching tabs would burn tokens. After a failure, a press still signs a new request. A moved version makes held answers stale, and the page refuses them.
- **No new generic tool.** `view_act` carries all three reads. The `diff` tool keeps its answer shape.
- **A card with View diff alone gets no read list.** This keeps a one-version card's bytes as they were.
- **A stop inside a path with two patches names both patches.** A stop can fall inside version 1's patch or between the two patches. The answer then says that version 2's patch stays out, as in "the last 12 lines of Version 1's patch of moved.txt, Version 2's patch of that file, and every path after it". The builder's review of `4b885c8b` found the earlier words false in that case: they said only "every path after moved.txt".
- **An omitted file stands in its own section.** On a rebased version, an omitted line goes under "Not read. A bound kept these out of every group:". It stands under no heading that names who changed it.
- **The read action IDs are reserved only on a card with `diffRead`.** A declared card can keep an act called `view-file-report`.
- **Commit IDs enter the model context.** The model can then name what the person reads. The context holds no patch text.

## Open limits

- **A manifest's base is its proposer's statement until the merge.** By reading, `propose-manifest` checks only that `base` has the form of a commit ID. So a proposer can name a commit that already holds an edit, and the edit then reads as "Changed only by the new base". View diff has the same trust in `base`. `packages/platform/src/reservation.ts` refuses a base that is not the destination's head, and an integration whose first parent is not the base. So such a version cannot merge. I read this and did not run it. The planner owns any earlier check.
- **The card's reason line shows a raw digest.** `apps/views/src/change.ts` builds the line from `context.definition`, and this head does not change that line. The builder owns the change, at the next edit of that card.
- **The deployed witness.** The planner names the room, and a person runs the script. J4's remaining phases gate it.
- **A retired staged ref hides a version.** Step `retire` deletes a version's ref, and an admin can run it. By reading, nothing retires a ref when a new version arrives. After a retirement, an interdiff from that version refuses and shows no lines. The planner owns any change to that rule.
- **Patches are coarse.** `boundedDiff` shows one hunk per file, from the first changed line to the last. Two far-apart edits read as a large replacement, and a rebase can then read as "cannot separate". The patch stays correct and applies with Git. The builder owns a line-level diff, if the planner asks for one.
- **No gutters or line colours.** The design packet draws them. The page keeps plain `pre.diff`. The builder owns them.
- **No rename detection.** A rename reads as one removal and one addition. The builder owns any change.
- **File buttons stop at 16 paths.** The answer lists at most 32 paths, and the page offers 16. It says how many more exist. A path that only the base changed has no button. The builder owns any change.
- **Four earlier versions.** A card offers an interdiff from the four nearest versions that name commits. The body lists every earlier version, and the generic `diff` tool reads any two commits.
- **Browser parity.** The room page has none. The request makes it optional.
- **The card fixture browser fails at main.** `packages/mcp/test/views-browser.mjs` times out at `fixture=incomplete`, waiting for a link, at main `d2e6c82c` and at `4b885c8b`. The gate does not run it, so it did not witness this head past that step. I left it, because it is outside this request. The planner owns it.
