# IE-1 and FG-1: item-effect guard and genesis definition check

## What changed

`isItemEffect` narrows `Effect | GenesisEffect` to `ItemEffect`. Its map has
exactly the keys of `ItemEffect["effect"]`, checked by `satisfies`. The fold
exports the guard beside `ItemEffect` and `changeItem`.

`applyEntry` throws `FoldError("the genesis seed names another definition")`
when a genesis seed names a declared definition digest other than the
provided definition's digest. The check runs before effects reach the
writer. A seed that names a platform definition still folds as before.

`212e97dd`, from `a5fb4a42`. The implementation promises are `204cf1a3` and
`9adca452`. Both promises state that source construction preceded filing;
delivery and review remained owed.

## Decisions and why

Ruling `8f63f164` permits both kernel changes under `docs/kernel.md`
section 7. The guard's list belongs with the kernel's effect type. The
fold's definition check agrees with `genesisJudged`, which already refuses
the same mismatch. The head adds the one guard export. It adds no scope
kind, platform definition, capability, refusal reason or journal form.

The guard accepts a genesis effect because `ItemEffect` holds a genesis
draft's encoded self and is not a subtype of `Effect`. The map's key type
rejects an omitted or extra item-effect kind. The `narrowed` type witness
requires the predicate; `unguarded` keeps an expected type error without it.
The runtime witness checks all 15 current effect kinds.

`applyEntry` keeps its signature. Request `586475dc` excludes the optional
changed-item-ID return. Callers retain their entry-verification and native
pin-resolution duties.

The six source call sites pass these definitions. No caller
intentionally folds a genesis under a different declared definition.
