# O-H2 append-work evidence

Independent evidence for ratified review `5643a940fde2c3c372d48ae89ee34e8e35593cf3` under the existing O3 request. All runs use isolated Git archives, never the integration checkout. `sources.json` records full source commits and SHA-256 hashes. `reviewer-rollback-bench.mjs` is an unchanged copy of the reviewer's reproducer; `append-work.mjs` reproduces its `bench` workload with isolated output paths, result assertions, counters and host metadata.

## Method

Run the identical command for each source archive, substituting only source/output paths:

```sh
node append-work.mjs <archive>/spike <output-directory> fixed
```

The journal starts with the O1 fixture's fixed keys, listing, and Bob's invitation and acceptance. Each backend is filled once to 100 entries, then 20 new offers are measured; the same journal is filled to 400, measures 20, then 1000 and another 20. Payload/action IDs follow the reviewer's `oN`/`mN` sequence. Intent nonces remain freshly generated by the runtime. Each measured operation includes intent construction, actor signing, authenticated Journal.submit, backend commit and semantic fold. Every offer must append once, be effective and not replay. No raw Context bypass, disabled authentication or runtime source patch is used.

A `moving` argument instead creates the fixture through `o3-fixture.create` and selects its declared handover profile; the remaining workload is identical. The accepted O1 and rejected aggregate baselines use `fixed`, as the reviewer's comparison did. Only the repaired source receives the additional moving-profile check, avoiding a duplicate quadratic baseline run.

The harness wraps Node's synchronous crypto `verify`/`sign` functions and the chosen backend's `entries()` method. Wrappers preserve return values and count only measured windows. `entriesReturned` counts logical rows returned by the API; it is not a direct allocation measurement. Counts reveal work even when host load affects elapsed time. All implementations receive the same wrappers. Timings are a single representative run on a shared host, not an exclusive-host benchmark or a statistical performance guarantee.

Each output directory contains incrementally written `result.json`, UTC window times, process CPU time, load averages, source/harness identity, per-window raw counts and normalized counts. Corresponding `.log` files retain stdout/stderr. SQLite database files remain isolated in those output directories. No timing-only test threshold is added.

Existing O1 already returns an increasing number of rows through `entries()`, and SQLite deserialization/fold cost grows with journal length. A successful O-H2 repair should therefore be described as removing repeated whole-prefix authentication and keeping added ordering work bounded; it must not be reported as making all append work constant.
